## Kiến trúc thực tế (đối chiếu mã nguồn 2026-08-16)

- **Frontend** `web/`: Vanilla JS, không build system. Planner ở `pages/sapxep.html` + `pages/phanmon.js`; FET engine chạy trong Web Worker (`pages/tkb-fet-engine.js`); bridge solve ở `pages/tkb-rust-bridge.js`. Trang quản trị `app.html` + `app.js` (Khối/Lớp/GV/Môn/Tiết chuẩn/Phân công) + `modules/admin-nav.js`; **Dạy ghép** (28/08) ở `modules/day-ghep.js`: `DATA.dayGhep` (nhiều lớp = học chung một tiết, nhiều môn, nhiều GV, số tiết, giới hạn, nhãn hiển thị tự động `Mã môn + Lớp` / `Mã - Lớp, Lớp` / `TIN/CN 6A1` hoặc viết tắt do người dùng đặt) được **chiếu** vào bảng phân công mỗi lớp một khoá: dòng một môn dưới **đúng khoá môn thật** `pccmMatrix["6.1|CLBTT"]="GV1, GV2"` (ô TKB lưu môn thật, chỉ nhãn là `ten` → Yêu cầu/bộ giải/thống kê áp như môn thường, viết tắt được trùng mã môn), dòng nhiều môn dưới **môn ảo** `["6A1|TIN/CN 6A1"]`; nên planner/RB/solver/xuất file dùng nguyên hợp đồng "Lớp|Môn". Planner hiện nhãn qua `tkbMonLabel` (ô lớp/GV/phòng, Chưa phân, xuất Excel/Word/Excel học sinh), kéo tay tiết chung vào lớp thứ hai không bị chặn (`tkbIsJointGhepPair`), gộp ô GV của tiết ghép chung (`tkbJointGhepRow`) không tô trùng lịch; bộ giải không tự xếp các lớp cùng giờ. Phân công chính chỉ còn 1 GV/ô, Thêm nhanh 1 môn – 1 GV; dòng do Dạy ghép sở hữu hiện chỉ xem (`pccmIsDayGhepRow`); tạo dòng một môn cho lớp đã có phân công chính → hỏi xác nhận rồi thay.
- **Backend** `rust_api/`: HTTP server **tự viết trên std** (TcpListener + thread), không Axum/Tokio. Dependency: argon2, serde_json, rusqlite, sha2. Auth = Argon2id + **session token opaque** (không JWT). Port local mặc định `1010` (`.env`, `TKB_RUST_PORT`).
- **Solver** `solver_runtime/`: Python 3.12 + OR-Tools CP-SAT/MILP; chạy trên Cloud Run (chính) và VPS (fallback), giao tiếp stdio protocol `tkb-reference-solver-stdio-v1`.
- **Dữ liệu**: SQLite KV store (`kvstore`), WAL mode; mỗi trường một key `school_{schoolId}`. Registry kết quả solve giữ trong RAM (TTL 6h, tối đa 64 bản) — restart service mất job đang theo dõi.
- **Luồng solve**: một nút Sắp xếp adaptive → precheck (`fresh_complete_first` / `repair_partial` / `refine_complete`) → Cloud Run → VPS Python → Rust native fallback. Chất lượng so sánh lexicographic: đủ tiết + hard-valid → 0 buổi 1 tiết → 0 gap ≥2 → tổng buổi GV → gap 1.
- **Nút 🍒 Cherry** (`tkbRunEngine('cherry')` → bridge → `settings.engine="cherry"` → `solver_runtime/src/tkb_engine_v3`): **một lượt duy nhất** 90s (xếp + tối ưu trong cùng lượt, không nối bậc thang tự tinh chỉnh). **Nút ▶ = FET thuần trong trình duyệt** (chỉ kiểm tra xếp đủ, không gọi backend). Engine tối ưu GV theo bậc có khóa: 1 tiết/buổi → khóa → trống ≥2 → khóa → buổi dạy/trống 1. **Không bao giờ rớt tiết ra Chưa phân vì chất lượng GV** (22/08 khuya — "bậc 4" đã gỡ): lịch đủ thì chỉ hoán đổi; buổi lẻ/trống ≥2 không gỡ được được **báo kèm gợi ý** (`solver.engine_v3.quality_unavoidable`, dòng "Chưa gỡ được N buổi…") để chủ trường tự xử lý mâu thuẫn ràng buộc. Bấm lại = tối ưu tiếp (warm-start, không bao giờ xấu hơn). Cổng bridge `cherryCandidateStrictlyBetter`: *số tiết xếp → 1 tiết/buổi → trống ≥2 → buổi dạy → trống 1*. **23/08 (trưa) — sửa lỗi "áp rồi tự hoàn tác"**: hậu kiểm `refinementStatisticsImproved` sau khi áp từng gọi lại cổng đọc lưới hiển thị (= ứng viên) nên bấm Cherry/Tối ưu v3 trên lịch đã đủ luôn bị hoàn tác với thông báo "không tốt hơn"; nay lượt Cherry so thẳng metrics ứng viên với lịch cũ đã chụp (`ignoreVisibleMetrics`), test `tools/tests/cherry_reclick_keep_test.js`. **23/08**: engine có *sàn "sức chứa"* (GV mà các buổi còn ≥2 ô hợp lệ không chứa hết tiết ⇒ buổi lẻ bắt buộc, được miễn trừ + báo lý do chính xác), liệt kê thêm nước *ghép sát tiết cùng môn* và *khối đôi ↔ 2 tiết lẻ* từ buổi khác, và toán tử *"ép ghép rồi sửa xung đột"* (`_force_pair_session`, kể cả chu trình đổi nhãn, nối tiếp 2 tầng) cho các buổi lẻ/trống ≥2 cứng đầu — trên TKB default đưa 1 tiết/buổi về đúng sàn cấu trúc. Chi tiết `docs/CHERRY_ENGINE.md`.
